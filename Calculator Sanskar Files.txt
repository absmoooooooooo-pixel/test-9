1. PURPOSE, SCOPE AND METHOD
================================================================================

1.1 Purpose
-----------
The project is a live engineering website, "Metal Weight Calculator", that
calculates the weight of metal parts (plates, sections, pipes, bars, cones,
spheres, flanges, dished heads, bolts and nuts). This document records how the
project is built, folder by folder and file by file, so that:

   - a new developer can find the correct file to edit;
   - the owner can see which files are shared and dangerous to change;
   - the calculation chain (input -> API -> result) is written down;
   - the generated files are clearly separated from hand-written files.

1.2 Scope
---------
Everything inside the project root was inspected:

   - the static website (root index.html, frontend/ and the seven language
     folders de, es, fr, hi, id, it, pt);
   - the Node.js calculation API (backend/);
   - the maintenance scripts (tools/);
   - the audit evidence folder (AUDIT_SAVED_CODE/);
   - configuration files, manifests, robots/sitemap/ads files, logs and images.

1.3 Method
----------
Every folder was listed, and the actual source text was opened and read. The
documentation was written from the code itself, not from file names. The main
evidence used:

   - the full folder inventory (443 files, about 17 MB);
   - HTML page structure (titles, sections, input ids, result ids, script and
     stylesheet links);
   - calculator JavaScript (validation, unit switching, API calls, rendering,
     drawing code, history configuration);
   - backend modules (routes, controllers, validation, weight chain, density
     tables, one module per shape family);
   - generated data files and the scripts that generate them;
   - project notes (README.md, DEPLOY.md, backend/README.md);
   - the audit reports and saved copies in AUDIT_SAVED_CODE/.

1.4 What this document is not
-----------------------------
This is not a redesign proposal and not a change request. No formula, layout,
colour, text or behaviour is recommended for change here; the sections about
risk only explain what happens if a file is edited.

1.5 Note on authorship
----------------------
The project folder is not a Git repository (there is no .git directory), so
there is no commit history to prove who created each file. Where the code or
project files contain no authorship evidence, this document states exactly:

   Creator information not available

Section 11 records all provenance that could be established.

2. PROJECT OVERVIEW AT A GLANCE
================================================================================

2.1 What the product is
-----------------------
A public website with 24 metal-weight calculators, a home page that lists them,
an About page, eight languages (English plus Hindi, Spanish, Portuguese, French,
German, Italian and Indonesian) and an installable web-app manifest.

Public domain used in the SEO files: https://metalweightcalculator.online

2.2 Two independent parts
-------------------------
PART A - The website (static files)
   - Root index.html (home page)
   - frontend/ (About page, 24 calculators, shared scripts and styles, icons,
     translations)
   - Seven generated language folders: de/, es/, fr/, hi/, id/, it/, pt/
   - Root web files: manifest.webmanifest, service-worker.js, robots.txt,
     sitemap.xml, ads.txt, .nojekyll
   These files can be hosted on any static host (the project notes name GitHub
   Pages). No server-side code is needed to display them.

PART B - The calculation API (Node.js, no dependencies)
   - backend/ contains all engineering formulas, density tables, validation,
     CORS, rate limiting and the HTTP routes.
   - It is deployed separately (any Node 18+ host) and is addressed by the
     browser through frontend/assets/js/api-config.js.
   - The API serves /api/* only; it never serves the website pages.

2.3 The key architectural rule
------------------------------
All engineering mathematics live in backend/calculations/ and
backend/core/weight.js. The browser pages collect and validate the typed
numbers, send them to POST /api/calculate/<calculator-slug>, and then only
format and display the returned numbers (plus draw the diagrams).

This rule is stated in README.md, backend/README.md, DEPLOY.md and in comments
inside the calculator scripts. It is the single most important thing to
understand before editing the site.

2.4 Technology summary
----------------------
   - HTML5, CSS3, plain JavaScript (ES5/ES2017-style, no framework).
   - No React, Vue, Angular, jQuery, Bootstrap or Tailwind.
   - No build step for the website: the HTML/CSS/JS files are served as written.
   - Node.js CommonJS backend with zero npm dependencies.
   - Python 3 maintenance scripts (dashboard data, internationalisation, SEO).
   - Tests: Node.js scripts (parity test, thread regression, DOM stub).
   - No TypeScript, no Webpack, no Vite, no package lock files, no root
     package.json.

4. FOLDER-BY-FOLDER ANALYSIS
================================================================================

4.1 PROJECT ROOT
----------------
Purpose
   Holds the published entry point (index.html), the site-wide web files
   (manifest, service worker, robots, sitemap, ads.txt), the documentation, the
   two main source folders (frontend/, backend/) and the maintenance scripts.

Why it exists
   Static hosts need one obvious home page. The root index.html is served as
   "/" automatically, and every other page is reached by a relative link. All
   links are relative so the same files work at a domain root and in a
   repository sub-path.

What it contains
   - index.html (home page)
   - README.md and DEPLOY.md (developer documentation)
   - manifest.webmanifest, service-worker.js, robots.txt, sitemap.xml,
     ads.txt, .nojekyll, .gitignore, .gitattributes
   - local run artifacts: backend-server.log / .err.log / .pid, taskkill.log,
     five working screenshots (cleanup-*.png, nut-bolt-icon-*.png)
   - the folders described below

Connections
   index.html loads frontend/assets/css/dashboard.css, frontend/shared/*.css,
   frontend/i18n/language-switcher.css, frontend/assets/data/dashboard-data.js,
   frontend/assets/js/dashboard.js, the shared scripts, and links every
   calculator card to frontend/calculators/<slug>/index.html.

Contribution to the site
   Essential. Without the root index.html the site has no home page; without
   the root manifest/service-worker it is not installable; without robots.txt
   and sitemap.xml search engines lose the crawl map.

Essential? Yes (the root index.html, manifest, robots and sitemap).
The log and screenshot files are not essential and are not referenced by any
page. They are local work artifacts.

Creator information not available (root web files and pages carry no author
metadata; the About page names the organisation, see section 11).

Essential? No.
Creator: the editor tool (generated file, not hand-written website code).

Contents

Connections

Contribution
   Documentation and evidence only.

Essential? No. Safe to keep, safe to move out of the published folder, but do
not edit the saved copies if they are used as audit evidence.

Creator information not available (the reports describe the audit work but do
not name the person who performed it).


4.4 backend/
------------
Purpose
   The calculation service: it receives the typed dimensions, validates them,
   applies the engineering formula, and returns finished numbers as JSON.

Why it exists
   To keep every formula, density value and validation rule in one private
   place, out of the public static files. The site can be viewed without it, but
   no calculator can produce a result without it.

What it handles
   - HTTP server and shutdown (server.js)
   - Request routing for /api/* (app.js, routes/index.js)
   - JSON parsing, body size limits, CORS, rate limiting (middleware/)
   - Material density tables (materials/)
   - Validation and the shared weight chain (core/)
   - One module per shape family (calculations/)
   - Controller glue between routes and modules (controllers/)
   - Configuration from environment variables (config.js, .env.example)
   - Tests and saved reference pages (test/)

Connections
   Called by frontend/assets/js/calc-api.js through POST /api/calculate/<slug>
   and GET /api/materials (plus /api/bootstrap.js, /api/health,
   /api/calculators). The slug is the same as the calculator folder name,
   enforced by calculations/index.js.

Contribution
   Essential for every calculation. It is deployed separately from the pages.

Files: see section 5.4.


4.4.1 backend/calculations/
   Purpose: hold the engineering mathematics, one module per family.
   Contents: prismatic.js (16 constant-section shapes), circularPlate.js,
   roundBar.js, solidCone.js, sphereBall.js, truncatedCone.js, flangePlate.js,
   dishEnds.js, nutBolt.js, and index.js (slug registry).
   Connections: controllers/calculationController.js looks up the slug here;
   every module imports core/weight.js and core/validation.js, and reads the
   density passed in the request (the browser obtains it from materials/).
   Essential: yes. This folder is the calculation engine.

4.4.2 backend/controllers/
   Purpose: thin glue. calculationController validates the slug, calls the
   module, and wraps the result in the standard response envelope;
   materialsController serialises the density tables for /api/materials and
   /api/bootstrap.js.
   Essential: yes.

4.4.3 backend/core/
   Purpose: the only weight chain and the only validation rules.
   weight.js: weightFromVolume (mm3 + g/cm3 -> kg, tonnes) and
   weightFromAreaKgM3 (dish heads).
   validation.js: unit factor (mm = 1, in = 25.4), numeric field reading,
   quantity rules, density range, finite-result guard, ValidationError class.
   Essential: yes. Every calculator depends on it.

4.4.4 backend/materials/
   Purpose: single source of truth for densities.
   Contains SECTION_MATERIALS (g/cm3, 7 materials), DISH_MATERIALS (kg/m3,
   6 entries including custom) and DENSITY_REFERENCE (15 reference rows for the
   tables shown on the pages).
   Essential: yes for correct densities; the frontend also has a small
   fallback copy so a page still opens if the API is unreachable.

4.4.5 backend/middleware/
   Purpose: HTTP plumbing.
   http.js: sendJson, sendText, readBody (size limit, JSON only), clientIp.
   cors.js: compares the request Origin against ALLOWED_ORIGINS.
   rateLimit.js: fixed-window counter per client IP for /api requests.
   Essential: yes for a safe public API.

4.4.6 backend/routes/
   Purpose: define the public API surface and the status codes
   (200, 204, 400, 401, 403, 404, 405, 413, 422, 429, 500).
   Essential: yes.

4.4.7 backend/test/
   Purpose: prove the migrated calculators still produce the same numbers as
   the pre-restructure pages.
   parity.js runs every page scenario against fixtures/original and against the
   API and compares rendered strings, history payloads and result objects
   (expected 71 pairs, PASS). threadFactors.js checks the fastener thread
   formulas. domStub.js provides the small DOM the old page scripts expect.
   Essential: no for runtime, yes for safe maintenance.

4.4.8 backend/test/fixtures/original/
   Purpose: frozen copies of the 24 original browser calculators, used only as
   the reference side of the parity test.
   Connections: read by test/parity.js through test/domStub.js.
   Essential: no for the website. Do not edit: the test compares against them.

Connections

Contribution
   It is the website. Essential.

4.5.1 frontend/about/
   Purpose: the About Us page (company introduction, what the site offers,

   It loads dashboard.css, the shared header/install/feedback styles, the
   language switcher and the shared connectivity/feedback/install scripts.
   Essential? No for calculations, yes for the published site's navigation

4.5.2 frontend/assets/
   Purpose: home-page-specific assets and the API client used by all

5.3 FRONTEND/ASSETS

5.3.1 frontend/assets/js/api-config.js
   Purpose: the single place that sets the API address:
       window.MW_API_BASE = "";
   Empty means "same origin". For a separately hosted API it holds that host.
   Why: the site is static, so the browser needs an absolute API address only
   when pages and API are on different hosts.
   Used by: every calculator page (loaded before calc-api.js).
   External: none (it is a configuration value).
   If edited: all calculators talk to the new host (or stop working if the URL
   is wrong). No formula, layout or density data is affected.
   If deleted: calc-api.js still works, but only with same-origin/local fallback
   logic, so a split deployment breaks.

5.3.2 frontend/assets/js/calc-api.js
   Purpose: the browser-side API client and the only network layer.
   Contents:
     - TIMEOUT_MS 15000 per request;
     - NOT_API_STATUSES [404, 405, 501] to detect a static host answering
       /api/* with HTML/404 instead of JSON;
     - FALLBACK_SECTION_MATERIALS and FALLBACK_DISH_MATERIALS (small copies of
       the density tables, used only if the API never answers);
     - baseUrlCandidates(): MW_API_BASE, an optional meta[name="mw-api-base"],
       the same-origin empty string, and on file:// or localhost a local
       backend address (http://127.0.0.1:8080);
     - request(path, options, track): fetch with timeout, JSON parsing, retry on
       a candidate base that does not behave like the API;
     - calculate(slug, payload): returns the shared result object,
       deduplicates concurrent calls and rejects stale ones;
     - abort/invalidation: AbortControllers are cancelled on input/change and on
       pagehide/beforeunload, so a late response can never overwrite newer input;
     - loadMaterials()/refreshMaterialFields(): GET /api/materials, merge into
       window.MW_MATERIALS and refresh <select id="material"> options;
     - window.MWCalc = { calculate, request, baseUrl, loadMaterials,
       getLastCalculationPromise }.
   Used by: all 24 calculator scripts (MWCalc.calculate) and the material
   dropdowns.
   External: the project's own backend API over HTTP(S).
   If edited: risk to every calculator. If deleted: no calculator can produce a
   result, although the pages still render and validate.

5.3.3 frontend/assets/js/dashboard.js
   Purpose: builds the home page tool explorer.
   Contents: reads window.ENGINEERING_DASHBOARD, renders category filter pills
   (#filterPills), groups tools into sections (#toolSections), builds each card
   with its inline SVG icon, tags and link, handles filtering and the mobile
   filter collapse, and removes the aria-busy state.
   Used by: index.html only.
   If edited: home page cards/filters change. If deleted: the home page shows an
   empty tools area (the data file alone does nothing).

5.3.4 frontend/assets/data/dashboard-data.js
   Purpose: the generated catalog of categories and tools.
   Contents: window.ENGINEERING_DASHBOARD = { categories: [9], tools: [24] };
   each category has id, name, description, icon, tone; each tool has id, name,
   category, path, and a long tag list for search/filter.
   Categories: Structural sections, Hollow sections, Solid bars & rods, Pipes &
   profiled bars, Fasteners, Plates & sheets, Spheres & balls, Cones & reducers,
   Vessel heads.
   Generated by: tools/generate_dashboard_data.py (header says so).
   Used by: dashboard.js.

5.3.5 frontend/assets/css/dashboard.css

   in the new unit. Results are always shown in kg, tonnes, m3, m2 and g/cm3 as

   /api/calculate/<slug> -> check finite -> render. If the service is
   unreachable, the error box shows the client's message ("The calculation
   service could not be reached..."); the page never calculates locally.

6.0 HOW EVERY CALCULATOR WORKS (the common engine)
---------------------------------------------------
All 24 pages share one architecture. To avoid repeating the same paragraph 24
times, this block describes the common behaviour; each calculator section below
lists only what is different (fields, formula, drawings, results, CSS).

  Page load
    1. The page renders the full HTML (including drawings and all text) before
       any script runs, so it is usable without JavaScript for reading.
    2. api-config.js sets the API base, then calc-api.js loads and starts
       GET /api/materials; the material dropdown is filled from
       window.MW_MATERIALS (server table or built-in fallback).
    3. unit-switch.js, dimension-values.js (22 pages), numeric-keypad.js,
       mobile-input-viewport.js, calculation-history.js, feedback.js,
       add-shortcut.js, smart-install-popup.js and
       internet-connection-manager.js attach their behaviour.
    4. The calculator script sets its initial state: unit mm, carbon steel,
       quantity 1, density readout, unit note, drawing at default proportions.

  Typing
    - Dimensions are <input type="number"> with inputmode decimal, Enter moves
      to the next field (the last field triggers Calculate), and the on-screen
      numeric keypad opens on phones/tablets.
    - After a first successful calculation, changing quantity or custom density
      re-runs the calculation automatically (autoRecalculate).

  Unit switch (MM / Inches)
    - Values already typed are converted (x25.4 or /25.4) and re-displayed;
      the exact millimetre value is remembered to avoid drift when switching
      back and forth.
    - The page sends the numbers with unit "mm" or "in"; the backend converts
      with 25.4. Drawings and dimension captions are redrawn with the new unit.

  Calculate
    1. validateInputs() checks every dimension (> 0, finite), quantity
       (whole, >= 1) and custom density (> 0); an error string stops the flow
       and shows in #error while hiding #results.
    2. The page collects the values and calls
       MWCalc.calculate("<slug>", { values, unit, density, quantity, material }).
    3. calc-api.js POSTs to <api base>/api/calculate/<slug> with a 15 s timeout,
       cancels stale requests, and retries local fallback bases on a non-API
       response.
    4. The backend validates again, runs the formula, and returns
       { ok, calculator, units, result }.
    5. The page checks the returned numbers are finite, stores lastCalculation,
       writes the result fields, shows the results card and enables auto
       recalculation.

      thread stress area, pounds, blank diameter or a station table.
    - If the API cannot be reached, the error box explains it; no result is
      invented locally.

6.22 FLANGE PLATE WEIGHT CALCULATOR
-----------------------------------
   Folder / slug: frontend/calculators/flange-plate/ ("flange-plate")

   UI
     - Two SVG drawings: a TOP VIEW (outer circle, bore, pitch circle, bolt
       holes) and a SECTION VIEW with hatch pattern and thickness.
     - Inputs Outer Diameter (OD), Inner Diameter (ID), Thickness (T), Number of
       Bolt Holes (N), Bolt Hole Diameter (HD), Bolt Hole Pitch Circle Diameter
       (PCD).

       input; flange-plate.js calls initDimensionValues and keeps them in sync.
     - Results: Single Flange Weight, Quantity, Volume Per Flange, Material

     - Formula card shows both the area form and the hole subtraction.

     - Bolt holes must stay outside the bore:

     - Bolt holes must stay inside the outer edge:

       rejected with "One of the dimensions is too large for this calculator."

     flange-plate.js draws the top view (scaled OD, ID, PCD, N holes evenly
     spaced, hole circles), the section view with hatching, and all dimension
     arrows/text. The hole pattern and the section both update live.

6.23 DISH ENDS (VESSEL HEADS) WEIGHT CALCULATOR
-----------------------------------------------
   Folder / slug: frontend/calculators/dish-ends/ ("dish-ends")
   Files: index.html, dish-ends.css (256), dish-ends.js (2047)
   Extra shared style: frontend/shared/dish-end-family.css

   UI structure (all blocks are revealed by the type selection)
     1. "Dish End Type" card with a select (#designType) containing:
          flat            -> "Flat Head - Dished"
          torispherical   -> "Torispherical Head"
          ellipsoidal     -> "Ellipsoidal Head"
          hemispherical   -> "Hemispherical Head"
          template        -> "Elliptical Head Template"
     2. Dimensions card (#dimensionsCard, hidden until a type is chosen):
          - MM/Inches switch;
          - one live SVG engineering drawing (#dishFigure > #dishDrawing)
            with dimension arrows and text drawn by JavaScript;
          - dynamic field grid (#fieldGrid) built per type;
          - for template only: "Number of Development Lines" buttons
            12 / 24 / 36 / 48 / 72 / 96 (#divisionBlock, default 24);
          - unit note.
     3. Material card (#materialCard): Material select (carbon steel, SS 304,
        SS 316, SS 316L, aluminium, Other/Custom), Material Density (kg/m3)
        field (default 7850, editable), Total Quantity (Pieces). A note explains
        that 7,850 kg/m3 is used unless another density is typed.
     4. Error box, actions bar (#actionsBar), results card (#results).
     5. Results:
          - TOTAL WEIGHT in kg + tonnes;
          - "Geometrical Results" (#geoRows): inside diameter, inside radius,
            knuckle/crown radius, height, arc angles, D/2H ratio (type-specific),
            dish surface area, straight face area, total developed area;
          - "Development Results" (#devRows): meridian length, developed blank
            diameter, blank area, and for template the divisions, angular step
            and station count;
          - coordinate table (template only): Division, Angle, Plan Radius,
            Height, Meridian Length, Blank X, Blank Y (#coordBody);
          - "Material Results" (#matRows): material, density kg/m3, plate
            thickness, material volume m3, estimated weight per piece, total
            quantity, total estimated weight, total developed area.
     6. Formula card (equation is replaced per type by the script), a step list
        per type, density reference table, FAQ (6 per type), related links.

   Inputs per type (backend TYPE_FIELDS)
     flat            id, kr, sf, t
     torispherical   id, kr, sf, t
     ellipsoidal     id, h, sf, t
     hemispherical   id, sf, t
     template        id, h, sf, t (+ divisions)
     Labels: Dish Inside Diameter (ID), Dish Knuckle Radius (R), Straight Face
     (SF), Dish Total Height (H), Dish Thickness (T).

   Calculation chain (backend/calculations/dishEnds.js)
     R  = ID / 2
     faceArea = 2 x pi x R x SF
     areaTotal = dishArea + faceArea
     blankDia = 2 x sqrt(areaTotal / pi)
     blankArea = (pi x blankDia^2) / 4
     weight = areaTotal x T x density / 1,000,000,000   (density kg/m3)
     totalWeight = weight x quantity

   dishArea per type
     flat:
       dishArea = pi x R^2
       The knuckle radius is used for the drawing (crown diameter ID - 2R,
       crown height H = R); the fillet surface is deliberately not added.
     torispherical:
       C.R = ID (crown radius fixed to the diameter)
       spread = C.R - K.R
       thetaC = asin(clamp((R - K.R) / spread, 0, 1))
       thetaK = pi/2 - thetaC
       H = C.R - sqrt(spread^2 - (R - K.R)^2)
       aKnuckle = 2 x pi x K.R x ((R - K.R) x thetaK + K.R x sin(thetaK))
       aCrown   = 2 x pi x C.R x (H - K.R x sin(thetaK))
       dishArea = aKnuckle + aCrown
       meridian = K.R x thetaK + C.R x thetaC
     ellipsoidal:
       semi-axes a = R, b = H
       dishArea = closed-form semi-ellipsoid surface:
         if a == b: 2 x pi x a^2
         if a > b: pi a^2 + (pi b^2 / (2e)) x ln((1+e)/(1-e)), e = sqrt(1 - b^2/a^2)
         if b > a: pi a^2 + (pi a b / e') x asin(e'), e' = sqrt(1 - a^2/b^2)
       meridian = meridianArc(R, H, pi/2)
     hemispherical:
       H = R; C.R = R
       dishArea = 2 x pi x R^2
       meridian = pi x R / 2
     template:
       same semi-ellipsoidal area as ellipsoidal, plus buildStations() writes
       the development coordinates for the chosen even division count.

   Validation
     ID > 0, T > 0, T < R, SF >= 0.
     flat/torispherical: K.R > 0 and K.R < R.
     ellipsoidal/template: H > 0 and H <= ID.
     template divisions: even whole number, 4..360.
     density: finite, > 0, between 1 and 25000 kg/m3 (readDensity options).

   Unit conversion
     The page sends unit mm or in and the backend multiplies every length by
     25.4. Density is never converted because it is always kg/m3 here. Display
     converts the returned millimetres back to the selected unit for the
     drawing/labels, while area is shown in mm2/m2 and weight in kg.

   Drawing logic
     dish-ends.js contains a drawing engine (arrow, dimension line, arc, hatch,
     text helpers) and one renderer per head type. It scales the selected
     profile to the figure viewBox, draws the wall thickness, the straight
     flange, the crown/knuckle radii, the ID and H arrows, and (for template)
     the development lines. Labels are drawn as SVG text by this file; that is
     why the page does not load dimension-values.js.

   Results / history
     weight text uses 2 decimals for kg and 4 for tonnes; areas use m2 with 6

6.24 NUT & BOLT WEIGHT CALCULATOR
---------------------------------
   Folder / slug: frontend/calculators/nut-bolt/ ("nut-bolt")
   Files: index.html, nut-bolt.css (1084), nut-bolt.js (3121)

   UI structure
     - Header, intro, then a category tab list (role=tablist):
         Bolts (#categoryBolts), Studs (#categoryStuds), Nuts (#categoryNuts).
     - A standards/product row: Standard (#standardSelect), Product
       (#productSelect), Size (#sizeSelect, which also offers "Custom
       dimensions"), plus a note (#standardNote) explaining the selected
       standard and that custom dimensions are typed manually.
     - Diagram area (#fastenerDiagramViews) filled by the script with the
       product's front/side (or top) drawing and its dimension symbols.
     - Dynamic dimension fields (#dimensionFields, role=tabpanel) built from the
       selected product; a dimension note (#dimensionNote) lists what is
       measured.
     - Material card: Select Material (7 metals + Custom Density), density
       readout, custom density input, Quantity (Pieces).
     - Error box, Calculate Weight, Reset.
     - Results: TOTAL WEIGHT in kg (#totalWeight, 3 decimals) plus pounds
       (#totalPounds), Unit Weight kg (#unitWeightKg) and lbs (#unitWeightLbs),
       Quantity (#resultQuantity), Volume Per Piece (#resultVolume, cm3),
       Thread Stress Area (#resultStressArea, mm2), Material Density
       (#resultDensity), and a dimensions summary (#resultDimensions).
     - Formula card "W = V x rho / 1,000,000", density table, FAQ (8), related
       calculators.

   14 products (backend/calculations/nutBolt.js and the page's PRODUCTS)
     Bolts:
       hex-ft        Hex Bolt, Full Thread       ISO 4017 / ASME B18.2.1
       hex-ht        Hex Bolt, Half Thread       ISO 4014 / ASME B18.2.1
       hex-blank     Hex Bolt Blank              ISO 4014/4017 head / ASME
       socket-head   Socket Head Cap Screw       ISO 4762 / DIN 912
       countersunk   Countersunk Socket Screw    ISO 10642 / DIN 7991
       carriage      Carriage Bolt               DIN 603
     Studs:
       stud-ft       Fully Threaded Stud         DIN 976-1
       stud-de       Double End Stud             DIN 938
       threaded-rod  Threaded Rod                DIN 976-1
     Nuts:
       hex-nut       Hex Nut                     ISO 4032 / ASME B18.2.2
       heavy-nut     Heavy Hex Nut               ISO 4033 / ASME B18.2.2 heavy
       jam-nut       Hex Jam Nut                 ISO 4035
       square-nut    Square Nut                  DIN 557
       lock-nut      Nylon Insert Lock Nut       ISO 7040
     Each standard provides a size table; the page also offers a "Custom
     dimensions" entry so the user can type every value.

   Fields (labels from FIELD_DEFS)
     Nominal Thread Diameter (d), Thread Pitch (P), Overall Length (L) (shown as
     Stud Length or Screw Length depending on the product), Thread Length (b),
     Second Thread Length (b2) for double-end studs, Width Across Flats (s),
     Head Height (k), Head Diameter (dk), Socket Width Across Flats (s), Socket
     Depth (t), Square Neck Width (a), Square Neck Height (f), Nut Height (m).
     Not every product uses every field; the script builds only the fields the
     product needs.

   Calculation logic (backend/calculations/nutBolt.js)
     1. Thread stress area:
          ISO metric:    As = (pi/4) x (d - 0.9382 x P)^2
          Unified inch:  As = (pi/4) x (d - 0.9743 x P)^2
        (the page also shows this area as a result).
     2. Product volume, in mm3, from the product's own geometry model:
          - hex head: prism across-flats x head height, minus a 30-degree top
            chamfer cone tangent to the flats;
          - socket head: cylinder + head, minus the hex socket pocket;
          - countersunk: conical head + shank, minus the socket;
          - carriage bolt: domed head + square neck + shank;
          - hex nut: chamfered hex prism minus the threaded bore;
          - heavy/jam/square/lock nuts: the same family with their own
            height/flat/bore dimensions;
          - studs/threaded rod: cylinder over the length, with thread length
            handled for the double-end type.
     3. Weight chain: weightFromVolume(volumeMM3, density, quantity), then
        totalPounds = totalWeight x 2.2046226218 (the page shows both units).
     4. Validation: positive dimensions, pitch > 0 for threaded products,
        thread lengths not longer than the overall length, quantity whole >= 1,
        density valid; geometry that cannot exist (for example a socket wider
        than the head) is rejected with a field message.

   Drawing logic
     nut-bolt.js draws each product with generated SVG (front view plus side/top
     view as appropriate), dimension arrows and symbols, using the standard
     size table values or the typed custom values. The drawing scales to the
     panel and redraws when the product, standard, size or unit changes.
     Because the labels come from this script, the page does not load
     dimension-values.js.

   Unit conversion
     Metric standards show mm; ASME standards show inch sizes and set the page
     unit to inches. The switch can still be used on custom dimensions. The API
     receives unit mm/in and converts by 25.4 like every other calculator;
     stress area is always returned in mm2 and shown that way, while volume is
     shown in cm3 and weight in kg and lbs.

   History
     window.CALCULATOR_HISTORY_CONFIG describes the selected product and its
     dimensions; mm and inch entries with the same physical size are stored as
     distinct records because the payload includes the unit.

   CSS
     nut-bolt.css contains the tab styling, standard/product/size row, dynamic
     field grid, diagram panels for each product family, result grid with two
     weight units, and responsive rules.

7.9 INPUT -> RESULT PATH (STEP BY STEP)
--------------------------------------
   1. The user types a dimension in frontend/calculators/<slug>/index.html.
      <slug>.js updates the drawing and dimension labels and stores the field
      in its values object.
   2. The user presses Calculate Weight (or Enter on the last field).
   3. <slug>.js validateInputs() checks the same rules the backend will apply
      and shows #error if something is wrong.
   4. <slug>.js builds the payload
        { values: {...}, unit: "mm"|"in", density, quantity, material }
      and calls MWCalc.calculate(slug, payload).
   5. calc-api.js aborts any previous request, POSTs JSON to
      <base>/api/calculate/<slug> with a 15 s timeout, and retries the
      fallback bases if the first answer is not the API.
   6. backend/routes/index.js checks CORS, method, optional API key and the
      per-IP rate limit, reads the JSON body, and calls
      calculationController.calculate(slug, body).
   7. The controller finds the module in calculations/index.js, normalises the
      unit to millimetres, validates every field, resolves the density (chosen
      material or custom value), runs the module's formula through
      core/weight.js, and builds
        { ok: true, calculator, units, result: {...} }
   8. The browser receives the JSON; <slug>.js checks the numbers, formats them
      (kg, tonnes, m3, m2, lbs, mm2 as relevant) and writes the result card.
   9. The result object is kept as lastCalculation; the History button can save
      it through calculation-history.js, and auto-recalculation is enabled for
      quantity/density changes.

10.6 FILES THAT CONTROL CALCULATION ACCURACY
--------------------------------------------
  Primary (order of impact):
    1. backend/calculations/<module>.js - the geometry formula per calculator.

  - Each <slug>.css has @media rules for the two-column diagram/input layout,

    chips and card sizes.
  - shared/calculator-sticky-header.css: ribbon collapse and menu behaviour.

    keyboard opens (visualViewport).
  - shared/numeric-keypad.js + numeric-keypad.css: keypad shown only for

  - dish-end-family.css and nut-bolt.css: horizontal scroll for wide drawings
    and tables instead of shrinking them to illegible sizes.

10.8 FILES RESPONSIBLE FOR PERFORMANCE
--------------------------------------
  - service-worker.js: pass-through by design; a caching version must be
    versioned or it will serve stale scripts.
  - calc-api.js: aborts stale requests, caches the density table once, 15 s
    timeout, avoids duplicate calculation while one is running.
  - Script loading order and `defer` on language-switcher.js; the rest are
    classic scripts at the end of <body>, so HTML paints first.
  - dashboard-data.js: the whole tool catalogue is loaded on the home page
    (small, one request); dashboard.js renders cards once.
  - Inline SVG drawings: no image downloads, but dish-ends.js (2047 lines) and
    nut-bolt.js (3121 lines) are the heaviest page scripts and redraw on input.
  - sitemap.xml is 258 KB and is fetched only by crawlers.
  - No web-font request, no CDN, no framework runtime, no bundling.
  - Page CSS is duplicated per calculator rather than shared, which costs
    repeated bytes across pages but allows independent styling; shared caching
    depends on the host's cache headers.

13.2 LOCAL RUN COMMANDS (from README.md)

  API:      cd backend && npm start          (http://127.0.0.1:8080)
  API dev:  cd backend && npm run dev        (node --watch)
  Tests:    cd backend && npm test
            expected: "calculator/scenario pairs compared: 71" then PASS
  Static:   serve the project root on port 8123 (any static server), for
            example python -m http.server 8123, then open
            http://127.0.0.1:8123/index.html
  The pages call http://127.0.0.1:8080 only when api-config.js is set to that
  base; otherwise they use the same origin.

13.3 CHECKLIST FOR ADDING A CALCULATOR
--------------------------------------
  1. Add backend/calculations/<name>.js exporting slug, validate, calculate.
  2. Register it in backend/calculations/index.js (slug -> module).
  3. Create frontend/calculators/<slug>/ with index.html, <slug>.css,
     <slug>.js following an existing page (plate is the reference).
  4. Include all shared CSS/JS in the same order, and define
     CALCULATOR_HISTORY_CONFIG at the end of <slug>.js.
  5. Add the tool entry through tools/generate_dashboard_data.py so the home
     grid and search include it.
  6. Run tools/generate_seo.py to add canonical/hreflang/JSON-LD and sitemap
     entries, then tools/build_i18n.py to copy the page into the 7 locales.
  7. Run backend tests and test one metric and one inch calculation.

13.4 DEPLOYMENT CHECKLIST
--------------------------
  - Static files (root index.html, frontend/, locale folders, manifest,
    service worker, robots, sitemap) to any static host.
  - backend/ to a Node >=18 host with PORT/HOST/PUBLIC_API_BASE/
    ALLOWED_ORIGINS set; never expose .env.
  - Point frontend/assets/js/api-config.js at the public API URL, or leave it
    empty when the API is served from the same origin.
  - Add the site origin to ALLOWED_ORIGINS when the API is on another domain.
  - Confirm /api/health returns the service name and 24 calculators.
  - After changing any cacheable script, bump its ?v= query in the pages (the
    project uses manual version query strings such as ?v=19).

13.5 KNOWN FRAGILE POINTS
--------------------------
  - The 24 CSS/JS files are copies, so a fix applied to one page does not
    reach the others; check whether the same bug exists on sibling pages.
  - The API must be reachable for any result; there is no client-side
    calculation fallback.
  - The density fallback table inside calc-api.js duplicates the backend
    table; if densities change in one place, update the other.
  - History entries are per tab (sessionStorage); closing the tab clears them.
  - Large drawings (flange, dish, nut-bolt) rely on horizontal scroll on small
    screens; CSS overflow rules must be kept.
