# Metal Weight Calculator

Engineering weight calculators for plates, sections, pipes, bars, cones, spheres,
flanges and dished heads.

The project is split in two:

- **Website** — static files: `index.html` at the repository root plus the pages
  and assets under `frontend/`. Hosted on GitHub Pages; no server needed to
  display it.
- **API** — `backend/`: the engineering formulas, material densities, validation
  and rate limiting. Deployed separately as a Node service.

## Text and labels — where to edit

Everything a visitor reads is plain source text: an HTML text node, an SVG
`<text>` element, or a JavaScript string. No image on the site carries interface
text — the only images the pages load are `frontend/icons/logo.png` (header) and
the favicon/PWA icons. Dimensions are drawn as SVG text, never as pictures.

| Text you see | Edit it in |
| --- | --- |
| Home headline, section headings, footer | `index.html` |
| Calculator card names, one-line descriptions, categories | `frontend/assets/data/dashboard-data.js` — generated by `tools/generate_dashboard_data.py`, so edit the curated lists in that script and re-run `python tools/generate_dashboard_data.py` |
| About page | `frontend/about/index.html` |
| A calculator's `<title>`, `<h1>`, input labels and placeholders, result labels, "Weight Calculation Formula", the worked example, FAQ, related links | `frontend/calculators/<slug>/index.html` — search for the text you can see |
| Drawing captions `FRONT VIEW`, `SIDE VIEW`, `SECTION VIEW`, `TOP VIEW` | the inline `<svg>` of that page: one `<text>` element per caption, carrying its own `x`, `y`, `fill` and `font-size` |
| Dimension symbols `D L W T E S K P` | the `<text id="dim…">` element in the same SVG — its text content *is* the symbol |
| Dimension values (`L = 100`) | generated at runtime in `frontend/shared/dimension-values.js`, which keeps the symbol text and appends `" = " + value` |
| Drawings built by script (`nut-bolt`, `flange-plate`, `dish-ends`) | that calculator's `.js` — their label, caption and annotation strings are all there |
| Unit note ("All dimensions are in millimeters.") | the calculator `.js` sets it on load and on unit switch, and the page `index.html` holds the same sentence as the no-JS default — change both |
| Validation and error messages | the calculator `.js` |
| Formula text and the worked example | page `index.html`; the maths itself lives in `backend/calculations/` |
| History, keypad, feedback, install pop-up | the matching `frontend/shared/*.js` |

Wording that repeats on every calculator — "Weight Calculation Formula",
"Frequently Asked Questions", "Related Calculators" and so on — is deliberately
kept in each page, so it stays in the HTML for crawlers and for visitors without
JavaScript. Change it everywhere at once with an editor-wide search and replace
(or `grep -rl` plus `sed`) across `frontend/calculators/*/index.html`.

## Languages

There is one English website. The language menu translates the current page in
place and never opens a language folder or changes the URL.

- English text in the pages is the source. Edit it there, as the table above says.
- `frontend/i18n/<code>.json` holds one dictionary per language (`terms`,
  `strings`, `templates`). Edit those files to change a translation.
- `python tools/build_i18n.py` regenerates `frontend/i18n/translations.js`, the
  single shared dictionary loaded by every page, and refreshes the language menu.
- `frontend/i18n/i18n.js` translates complete interface strings only. Formulas,
  dimensions, units, standard names and numbers do not match the dictionary, so
  they stay unchanged; calculator values and selected options are never touched.
- `python tools/generate_seo.py` refreshes the English canonical/metadata block
  and the 26-URL sitemap after pages change.

`AUDIT_SAVED_CODE/` is review evidence (saved drawings, screenshots, reports).
Nothing links to it.

## Hosting

- **Website:** GitHub Pages serves the root `index.html` as the home page — see
  [DEPLOY.md](DEPLOY.md).
- **API:** deployed on its own Node host. The browser finds it through
  `frontend/assets/js/api-config.js`:

  ```js
  window.MW_API_BASE = "https://api.example.com";
  ```

  Leave it empty only when one host serves both the pages and the API.

No API key or secret is stored in frontend files. The API allows the site's
origin through `ALLOWED_ORIGINS`; everything else is refused.

## How the split works

1. The page reads and validates the user's inputs exactly as before (messages
   and rules live in the page).
2. The page `POST`s the values with `frontend/assets/js/calc-api.js` to
   `<API base>/api/calculate/<calculator>`.
3. The backend validates the payload again, runs the engineering formula and
   returns the finished numbers.
4. The page renders those numbers with its existing formatting, drawings,
   history entries, print and PDF code.

Material densities come from the API (`/api/materials`), with a built-in
fallback for the common materials so the page still opens if the API is
unreachable.

The engineering formulas — areas, volumes, surface areas, blank diameters, hole
removal, weights and tonnes — exist **only** in `backend/calculations`.

### API

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/health` | Service check |
| `GET` | `/api/calculators` | Slugs the API serves |
| `GET` | `/api/materials` | Density tables as JSON |
| `GET` | `/api/bootstrap.js` | Densities as a script (tooling and tests) |
| `POST` | `/api/calculate/:calculator` | Runs one calculation |

Example:

```bash
curl -X POST https://api.example.com/api/calculate/plate \
  -H "Content-Type: application/json" \
  -d '{"values":{"width":1000,"thickness":5,"length":2000},"unit":"mm","density":7.85,"quantity":3}'
```

```json
{"ok":true,"calculator":"plate","units":{"dimensions":"mm","density":"g/cm3"},
 "result":{"areaMM2":5000,"volumeMM3":10000000,"volumeM3":0.01,
           "singleWeight":78.5,"totalWeight":235.5,"totalTonnes":0.2355,
           "materialName":"Custom Material"}}
```

Errors are always JSON: `400` invalid input (with the field name), `401` missing
API key when one is configured, `403` origin not allowed, `404` unknown
calculator, `405` wrong method, `413` body too large, `429` rate limited, `500`
unexpected.

`dish-ends` takes an extra `type` (`flat`, `torispherical`, `ellipsoidal`,
`hemispherical`, `template`) and a density in **kg/m³**; every other calculator
uses **g/cm³**.

## Security

- The API process serves `/api/*` only; the website is static and contains no
  formulas.
- Inputs are validated and range-checked on the server, not just in the browser.
- CORS allows listed origins (`ALLOWED_ORIGINS`); anything else gets `403`.
- `/api/calculate` is rate limited per client IP (`RATE_LIMIT_MAX` per
  `RATE_LIMIT_WINDOW_MS`).
- Request bodies are capped (`MAX_BODY_BYTES`) and only JSON is accepted.
- Configuration comes from the environment (`backend/.env`, git-ignored).

## Tests

```bash
cd backend
npm test
```

The parity test runs every calculator twice with identical inputs — once with the
pre-restructure page (kept in `backend/test/fixtures/original` as reference
material only) and once with the migrated page calling the API — and compares
every rendered string, the calculation history payload and the result object.
The five dish head types are compared field by field, including the template
station table. It starts its own temporary API server, so no setup is needed.

Expected result: `calculator/scenario pairs compared: 71` followed by `PASS`.
